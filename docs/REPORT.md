# Отчёт по проекту: генератор продающих описаний товаров (тема №14)

## 1. Постановка задачи

По характеристикам товара (название, категория, ключевые особенности, цена, целевая аудитория, бренд) система
генерирует продающее описание для карточки товара. Описание учитывает стиль бренда (нейтральный, эмоциональный,
премиальный, молодёжный, экспертный) и требования площадки: **Ozon**, **Wildberries** или собственный сайт.

Требования к результату:

- упомянуты **все** ключевые особенности, причём раскрыты через выгоды для покупателя;
- нет запрещённых и непроверяемых формулировок («лучший в мире», «100% гарантия», медицинские обещания);
- цена и факты не искажены, ничего не выдумано;
- соблюдены тон бренда и формальные правила площадки: длина, отсутствие ссылок и эмодзи на маркетплейсах.

## 2. Архитектура

### 2.1. Мультиагентная система

Готовые агентные фреймворки не используются. Все агенты наследуются от абстрактного `Agent`
(`backend/agents/base.py`) с методом `async process(state) -> state`, хранят имя, последний результат и метаданные
последнего LLM-вызова. Агенты обмениваются общим состоянием `AgentState` (Pydantic): товар, контекст RAG и
справочника, текст, ошибки и предупреждения, оценки, лог.

| Агент | Что делает | LLM |
|---|---|---|
| `DescriptionGenerator` | собирает промпт из характеристик, требований площадки и стиля, выгод, продающих фраз, шаблонов, запрещённых формулировок и примеров RAG | да, `temperature=0.8` |
| `Validator` | правила: длина под площадку, покрытие каждой особенности (по основам слов, snowball-стеммер), запрещённые фразы с учётом словоформ, совпадение цены, ссылки и эмодзи, слова, противоречащие тону, упоминание названия и бренда, повторы, частотные слова, «!!!» и КАПС | опционально: проверка выдуманных фактов, `temperature=0` |
| `Critic` | LLM-as-a-Judge: пять критериев 0–10 и общий балл, few-shot (хороший и плохой примеры), рекомендации. При таймауте или битом JSON возвращает fallback-оценку 5.0 | да, `temperature=0.1`, JSON-режим |
| `Editor` | исправляет текст по ошибкам Validator и советам Critic. Не вызывает LLM, если замечаний нет. Возвращает флаг `editor_changed` | да, `temperature=0.5` |
| `Supervisor` | Проверяет черновик и выделяет до трёх правок по первой оценке и замечаниям. Если правка снижает оценку, нарушает правила или её не удалось проверить, возвращает предыдущую версию. Успех требует пройденной валидации и достоверной оценки от 7 | — |

**Лог рассуждений.** На каждом шаге Supervisor записывает `ReasoningStep`: агента, краткие вход и выход, модель и
её параметры (температуру), время начала и конца, статус (`ok/warning/error`), ошибку и вложенные LLM-вызовы. Лог
сохраняется в таблицу `reasoning_logs` и в `logs/app.log`. Получить его можно через
`GET /api/v1/requests/{id}/reasoning_log`, а посмотреть — на странице «Логи рассуждений» (там же таймлайн шагов).

**Трассировка LLM (свой аналог LangSmith).** Контекст запроса и агента передаётся через `contextvars`
(`backend/utils/tracing.py`), поэтому любой вызов `LLMManager` автоматически помечается `request_id` и именем
агента. `LLMCallLogger` пишет в `llm_calls` и в JSON-лог `logs/llm_calls.log` провайдера, модель, параметры, хэши
промпта и ответа, первые 300 символов промпта и ответа, токены, задержку, статус и ошибку. Неудачные попытки перед
fallback тоже логируются.

### 2.2. RAG

- **BM25** (`rank_bm25`) по основам слов. Кандидатом считается любой документ с общим термином: в маленьком корпусе
  IDF частого слова бывает нулевым, и без этого правила такие документы терялись бы.
- **Векторный индекс**: Qdrant с cosine-метрикой и фильтрами по категории, площадке и стилю. В Docker это сервер,
  локально и в тестах — in-memory режим `qdrant-client`, без библиотеки — numpy-индекс с тем же интерфейсом.
- **Эмбеддинги**: `paraphrase-multilingual-MiniLM-L12-v2` (118M параметров, 384 измерения). Это синглтон с ленивой
  загрузкой. Если torch недоступен, используется детерминированный `HashingEmbedder` (feature hashing основ слов и
  символьных триграмм).
- **Объединение**: Reciprocal Rank Fusion `Σ w_i/(k + rank_i)`, `k=60`, затем лёгкий reranker с бонусом за
  совпадение площадки и стиля.
- Найденные примеры подаются в промпт с инструкцией «перенимай приёмы, не копируй факты». Справочник даёт выгоду
  для каждой особенности (сопоставление по основам слов), продающие фразы категории, шаблон структуры и список
  запретов.

### 2.3. LLM-бэкенды

`LLMManager` принимает строку модели `provider:model`. Цепочка провайдеров по умолчанию:
`ollama → openai → anthropic → openrouter → groq → hf → mock`. Недоступные провайдеры (нет ключа, нет сервера)
пропускаются, при ошибке включается следующий. Явно выбранный провайдер ставится первым. В скрипте оценки
недоступный провайдер считается ошибкой, а не тихой подменой: так в таблицу не попадут чужие результаты.

| Бэкенд | Модели и размеры | Назначение |
|---|---|---|
| Ollama (`/api/generate`) | `qwen2.5:7b` (7.6B), `qwen2.5:3b` (3.1B), `qwen2.5:1.5b` (1.5B) | основной локальный вариант; семейство Qwen2.5 выбрано за качество русского языка в диапазоне 1–13B |
| HuggingFace Transformers | `Qwen/Qwen2.5-0.5B-Instruct` (0.5B) | запасной вариант без Ollama, работает на CPU; асинхронная обёртка над `pipeline`, LRU-кэш |
| OpenAI / OpenRouter / Groq | `gpt-4o-mini`, `qwen/qwen-2.5-7b-instruct`, `llama-3.1-8b-instant` | OpenAI-совместимый Chat Completions |
| Anthropic | `claude-haiku-5-5` | Messages API |
| `mock` | правила, без весов | офлайн-режим, тесты, CI, демонстрация без GPU |

Модели разных размеров (0.5B → 1.5B → 3B → 7B) позволяют сравнить качество со стоимостью и скоростью. 7B даёт
лучший русский текст и надёжнее возвращает JSON для Critic. 1.5–3B подходят для слабых машин. 0.5B — это
CPU-fallback: такая модель часто ломает JSON, и здесь срабатывает fallback-логика Critic.

### 2.4. Остальные компоненты

- **FastAPI** (`backend/api`): генерация (одиночная, мульти-вариант, пакет, CSV, ансамбль), администрирование,
  оценка, HITL, логи, мониторинг, `/health`. JWT (PyJWT), bcrypt, роли `user/editor/admin`.
- **БД**: async SQLAlchemy, PostgreSQL 16 в Docker и SQLite локально. 11 таблиц, включая `reasoning_logs` и
  `llm_calls`.
- **Кэш**: таблица `cache` (ключ — SHA-256 от товара, режима, провайдера и модели; счётчик `hits`; TTL), плюс
  Redis при `USE_REDIS_CACHE=true`.
- **Celery**: пакетная генерация, `evaluate_model_task`, `compare_models_task`, пакетная оценка, переиндексация,
  массовый импорт, очистка кэша (beat по расписанию). Задачи обновляют статус `PROGRESS` и пишут результаты в БД.
  Без брокера работает eager-режим в отдельном потоке.
- **Human-in-the-Loop**: в очередь `uncertain_examples` попадают результаты с низкой оценкой, ошибками валидации,
  fallback-оценкой Critic или отзывом ≤ 2/5. Редактор подтверждает (с правкой) или отклоняет. Подтверждённый
  пример сразу добавляется в `knowledge_base` и в индексы BM25 и Qdrant, то есть начинает участвовать в RAG.

## 3. Данные

Открытых русскоязычных датасетов «характеристики → продающее описание» с разметкой по стилю и площадке нет, а
парсинг маркетплейсов противоречит их правилам. Поэтому датасет **сгенерирован** воспроизводимо (`seed=42`) из
вручную составленного каталога предметной области (`scripts/data_catalog.py`). В каталоге 12 категорий, по 8 типов
товаров, 6 брендов, 12 особенностей с выгодами, 5 аудиторий, диапазон цен и существительные с указанием рода для
согласования продающих фраз.

| Набор | Объём | Состав |
|---|---|---|
| База знаний | 1200 | пары «характеристики → описание», по 100 на категорию; стиль и площадка равномерно |
| Справочник | 737 | 528 продающих фраз, 144 выгоды «особенность → польза», 50 запрещённых формулировок, 15 шаблонов «площадка × стиль» |
| Тест | 200 | товары не пересекаются с базой знаний по названию |

Эталонные описания собираются из шаблонов, свои для каждого стиля (вступление, подача особенности, обращение к
ЦА) и каждой площадки (Ozon — блок «Преимущества», WB — короткие абзацы, сайт — история, цена и призыв к
действию). Формулировки выбираются случайно.

## 4. Метрики

| Метрика | Реализация | Что измеряет |
|---|---|---|
| BLEU | `sacrebleu`, sentence BLEU с exp-сглаживанием; дополнительно corpus BLEU | n-граммная точность относительно эталона |
| chrF++ | `sacrebleu` `CHRF(word_order=2)` | F-мера по символьным 1–6-граммам и словным биграммам, устойчива к морфологии |
| ROUGE-L | своя реализация: LCS по основам слов, F-мера с β=1.2 | полнота покрытия эталона; `rouge-score` выбрасывает кириллицу |
| METEOR | своя реализация: точное совпадение, затем по основе; Fmean (α=0.9) со штрафом за фрагментацию | выравнивание с учётом словоформ; WordNet в `nltk` есть только для английского |
| BERTScore | `bert-score` (`bert-base-multilingual-cased`), без torch — косинус эмбеддингов (бэкенд указан в результате) | семантическая близость |
| Exact Match | нормализованное совпадение | для полноты набора; для длинных текстов почти всегда 0 |
| keyword_coverage | доля ключевых особенностей, найденных в тексте по основам слов | главная прикладная метрика задачи |
| sentiment | лексиконная тональность: доля позитивных маркеров | продающий текст должен быть позитивным |
| style_accuracy | TF-IDF (символьные 2–4-граммы) + логистическая регрессия, обучена на базе знаний | соответствие заданному стилю |
| composite | среднее BLEU, chrF++, ROUGE-L, METEOR, BERTScore и keyword_coverage | критерий выбора победителя при сравнении |

Для каждой метрики считается bootstrap 95%-интервал (1000 повторов). Отличие режима от `baseline` проверяется
парным bootstrap и парным t-тестом (`scipy.stats.ttest_rel`).

## 5. Результаты

### 5.1. Что измерено

Все режимы прогнаны на выборках 20, 50 и 100 тестовых товаров (стратификация по 12 категориям, `seed=42`). LLM —
детерминированная заглушка `mock`, эмбеддинги — `hashing-384`. Реальная LLM в прогоне не участвовала, по двум
причинам:

- на машине разработки не удалось запустить Docker Desktop и не установлен Ollama;
- скачивание весов с HuggingFace шло со скоростью около 0,1–0,3 МБ/с, этого не хватило даже на `Qwen2.5-0.5B`.

Поэтому числа ниже проверяют **конвейер оценки и вклад компонентов**, а не качество языковой модели. Команда для
прогона на Qwen приведена в README.

| режим | n | BLEU | chrF++ | ROUGE-L | METEOR | BERTScore (emb.) | keyword cov. | style acc. | composite |
|---|---|---|---|---|---|---|---|---|---|
| baseline | 100 | 0.233 | 0.446 | 0.400 | 0.406 | 0.704 | 0.929 | 0.370 | 0.520 |
| +dict | 100 | 0.407 | 0.627 | 0.631 | 0.642 | 0.825 | 1.000 | 0.340 | 0.689 |
| +rag | 100 | 0.435 | 0.642 | 0.647 | 0.652 | 0.829 | 1.000 | 0.640 | 0.701 |
| +agents | 100 | 0.435 | 0.642 | 0.647 | 0.652 | 0.829 | 1.000 | 0.640 | 0.701 |
| +ensemble | 100 | 0.435 | 0.642 | 0.647 | 0.652 | 0.829 | 1.000 | 0.640 | 0.701 |

Таблицы для n=20 и n=50 есть в README и в `results/mock/eval_summary.md`. Графики: `results/mock/eval_bar.html`
и `results/mock/eval_radar.html`.

### 5.2. Значимость

Отличия от `baseline` (парный bootstrap на 2000 повторов и парный t-тест, файл `results/mock/significance.json`):

| сравнение | n | Δ chrF++ | p (bootstrap) | p (t-тест) | Δ keyword cov. | p (t-тест) |
|---|---|---|---|---|---|---|
| +dict vs baseline | 20 | +0.172 | < 0.001 | 1e-15 | +0.035 | 0.085 |
| +rag vs baseline | 50 | +0.192 | < 0.001 | 2e-22 | +0.064 | 7e-05 |
| +rag vs baseline | 100 | +0.197 | < 0.001 | 3e-45 | +0.071 | 2e-09 |

При n=20 прирост покрытия особенностей ещё не значим по t-тесту (p=0.085), при n=50 и 100 значим. Это наглядно
показывает, зачем нужны выборки разного размера.

### 5.3. Интерпретация

- Справочник выгод даёт основной прирост n-граммных метрик и гарантирует упоминание всех особенностей.
- RAG почти не меняет BLEU, но поднимает точность стиля с 0.34 до 0.64: модель перенимает композицию примеров того
  же стиля и площадки.
- На заглушке `+agents` и `+ensemble` не отличаются от `+rag`. Первый же черновик проходит проверки, поэтому Editor
  не вызывается, а варианты заглушки дают одинаковый текст. Работа цикла Validator → Critic → Editor проверена
  юнит-тестами (`tests/unit/test_agents.py`): исправление после низкой оценки, остановка по `max_iterations`,
  fallback Critic. Её вклад в метрики нужно измерять на реальных моделях, которые ошибаются чаще.
- Синтетические эталоны собраны из тех же формулировок, что и справочник, поэтому абсолютные значения BLEU и chrF++
  завышены. Сравнивать корректно только режимы между собой.

## 6. Логирование и мониторинг

- `logs/app.log` (ротация 5×5 МБ) — текстовый или JSON-формат (`LOG_JSON=true`), в каждой строке `request_id` и
  агент из contextvars. Уровни по модулям задаются через `LOG_LEVELS`.
- `logs/llm_calls.log` — JSON-трасса каждого LLM-вызова. Таблицы `llm_calls` и `reasoning_logs` доступны через API.
- `GET /api/v1/health`: БД, векторный индекс, база знаний, доступность каждого LLM-провайдера, Redis.
  `GET /monitoring/stats`: кэш (записи, попадания, топ), вызовы LLM по провайдерам и статусам (число, средняя
  задержка, токены), генерации по режимам (средняя оценка Critic, время).
- Middleware пишет каждый HTTP-запрос с кодом и временем, в ответ добавляется заголовок `X-Request-ID`.

## 7. Тестирование

88 тестов (pytest + pytest-asyncio), **покрытие 95%** (`pytest --cov=backend`):

- агенты: правила Validator, парсинг JSON Critic и fallback, условный вызов Editor, полный цикл Supervisor
  (успех, `max_iterations`, остановка без изменений, ошибка генератора) с сохранением лога в БД;
- retrieval: BM25, векторный индекс (Qdrant in-memory и numpy), RRF с весами, гибридный поиск, reranker;
- LLM: Ollama и внешние API через `httpx.MockTransport` (успех, 4xx/5xx, таймаут), HF через подмену pipeline,
  fallback-цепочка `LLMManager` с проверкой записи в `llm_calls`;
- метрики и значимость, классификатор стиля, отчёты и графики;
- кэш (TTL, hits, очистка), HITL (очередь, подтверждение с обновлением индекса), обратная связь;
- Celery-задачи в eager-режиме, скрипты `generate_data`, `import_data`, `create_admin`, `run_eval`;
- интеграционные тесты всех групп эндпоинтов через `TestClient`, включая роли и права доступа.

## 8. Сложности и решения

| Проблема | Решение |
|---|---|
| `rouge-score` и METEOR из `nltk` не работают с русским | свои реализации ROUGE-L и METEOR на snowball-основах |
| BM25 терял документы, если IDF частого слова равен 0 | кандидатом считается любой документ с общим термином |
| `asyncio.run` внутри Celery-задачи конфликтует с циклом FastAPI в eager-режиме | задача запускается через `asyncio.to_thread(task.apply)`, у задачи свой контейнер с `NullPool` |
| Маленькие модели ломают JSON | толерантный `extract_json` (code fence, висячие запятые, одинарные кавычки) и fallback 5.0 с отправкой в HITL |
| Модель переносит факты из примеров RAG | инструкция «не копируй факты»; Validator ловит выдуманную цену; опциональная LLM-проверка фактов |
| При тихом fallback в оценке результаты одной модели выдаются за другую | `run_eval` требует доступности указанного провайдера, а в отчёт пишется `models_actually_used` |
| Несогласованные по роду продающие фразы в справочнике («качественный деталь») | у существительных в каталоге указан род, прилагательное согласуется функцией `agree()` |

## 9. Ограничения и развитие

- Синтетический датасет завышает n-граммные метрики для режимов, которые копируют структуру примеров. Следующий
  шаг — разметить 200–300 реальных карточек и оценить на них вручную и через Critic.
- LLM-as-a-Judge на той же модели, что и генератор, склонен к самооценке. Для чистоты эксперимента Critic лучше
  запускать на другой, более крупной модели.
- Возможные улучшения: cross-encoder reranker, MLflow для экспериментов, генерация нескольких вариантов с
  A/B-оценкой пользователями.
